This page is not a claim to list every dataset in existence. It is an **expandable experiment-planning reference** for choosing data and experiment scale from the research question, modality, conditioning, scale, access constraints, storage, and compute budget.

:::caution[Licenses and availability change]
Dataset licenses, download mechanisms, URL survival, and versions can change. Re-check the official source before training or redistributing data, especially for web-scraped image/video corpora, medical datasets, and autonomous-driving data. “Public download” does not mean unrestricted commercial use or redistribution.
:::

## Start from available GPU / storage

The planner below does not assign one fixed VRAM requirement to a dataset. It estimates a **dataset + model / experiment profile** and classifies each candidate as comfortable, tight-but-feasible, sharding-required, or a collaboration / cluster candidate.

:::note[GPU count does not simply add VRAM]
Ordinary DDP keeps a model replica on each GPU, so `4 × 24 GB` is **not** equivalent to one 96 GB GPU. FSDP, ZeRO, tensor/model parallelism, or other sharding methods are needed to distribute model / optimizer state.
:::

## Compute budget is part of experiment design

Dataset size and GPU VRAM are not one-to-one. Memory / training cost is usually driven by:

1. **backbone size** — DiT-B / L / XL, video transformers, and VLA backbones differ greatly in activation and optimizer-state cost;
2. **input size** — image resolution, video frames, trajectory horizon, point/token count;
3. **representation** — pixel vs latent training, frozen encoders / VAEs, precomputed embeddings;
4. **autodiff complexity** — MeanFlow JVPs, divergence estimators, and higher-order derivatives can cost more memory than ordinary forward/backward;
5. **optimizer / precision** — FP32, BF16 / FP16, Adam states, 8-bit optimizers;
6. **distributed strategy** — DDP vs FSDP / ZeRO / tensor parallel and activation checkpointing;
7. **data pipeline** — video decoding, RGB-D / lidar, web crawling, and robot-trajectory caching can become CPU / SSD / network bottlenecks before GPU compute.

The planner therefore labels VRAM/GPU values as **planning estimates**. When a paper or official repository reports a concrete training setup, the reproduction note should prefer the paper-reported hardware and batch configuration.

## How to choose a dataset

1. Match the **output modality**: image, video, action trajectory, waveform, molecular graph, time series, or 3D pose.
2. Match the **conditioning**: unconditional, class, text, image context, robot state, language instruction, map/sensor input, or physical property.
3. Use **small data for smoke tests, then scale**: CIFAR-10, AFHQ, KTH, QM9, UCR/UEA, or MedMNIST can expose implementation bugs cheaply; ImageNet, DROID, LAION, and Waymo are better after the method is stable.
4. Ensure the data actually supports the **research question**. Long-horizon action research needs trajectories; probability-path research can benefit from synthetic systems with known dynamics.
5. Preserve **benchmark continuity**. For direct comparison with MeanFlow-family papers, ImageNet-1K 256×256 is often more valuable than a larger but incomparable dataset.
6. Budget for **storage and preprocessing**, not only GPU training. Web-scale image-text, video, RGB-D, and lidar data can be dominated by download, decoding, caching, tokenization, and I/O costs.
7. Pin **versions and governance**. Dynamic databases and URL-based corpora require release/crawl dates; medical data may require credentialing and DUAs.
8. Watch **train/eval leakage**, especially when web-scale pretraining may overlap COCO, ImageNet, captions, or downstream benchmarks.

## Task families

| Task family | Typical research question | Good starting points |
|---|---|---|
| Image generation | one/few-step quality, FID, mode coverage | CIFAR-10 → AFHQ / FFHQ → ImageNet-1K |
| Text-to-image / multimodal | alignment, conditioning, large-scale pretraining | COCO, CC3M / CC12M, LAION-5B, DataComp |
| Segmentation / structure | masks, layout conditioning, dense prediction | SA-1B, ADE20K, Cityscapes, Open Images |
| Video | temporal consistency, prediction, dynamics | KTH, UCF101, Kinetics, Something-Something, Ego4D |
| Robot action | BC, multitask, long horizon, cross embodiment | RoboMimic, BridgeData V2, DROID, LIBERO, Open X-Embodiment |
| Autonomous driving | motion forecasting, scene generation, sensor fusion | Argoverse 2, Waymo, nuScenes, KITTI, BDD100K |
| Speech / audio / music | waveform generation, TTS, events, music | LJSpeech, LibriTTS, LibriSpeech, AudioSet, FSD50K, MAESTRO |
| Text / LLM | pretraining, filtering, long context | WikiText-103, OpenWebText, C4, The Pile, FineWeb |
| Molecule / protein / material | validity, conformations, protein/crystal generation | QM9, MOSES, GEOM, PDB, UniRef50, Materials Project |
| Time series / dynamics | forecasting, trajectory generation, known dynamics | UCR/UEA, ETT, M4, Electricity, Lorenz / FitzHugh–Nagumo |

## Dataset / compute metadata to record for every experiment

At minimum record: **dataset version / release date, train-val-test split, actual sample count used, resolution / sampling rate, preprocessing, augmentation, conditioning fields, whether latents/embeddings are precomputed, filtering/deduplication, license/access date, evaluation subset, metric implementation, GPU model/count, precision, global/per-GPU batch size, gradient accumulation, optimizer, activation checkpointing, distributed strategy, wall-clock time, peak VRAM, and checkpoint/cache storage**.

For robotics also record **embodiment, camera placement, action representation, control frequency, trajectory horizon, and whether failure episodes are retained**. For time series record **sampling interval, forecast horizon, normalization, and missing-value policy**. For molecule/3D tasks record **graph/coordinate representation, canonicalization, and conformer/structure filtering**.
